# Category pages

Status: **live** — generated by `tools/build-categories.mjs` into `docs/index.html`
and `docs/<slug>/`

Six pages, one per category, each listing the printables in it, plus the
catalogue index at `/` that gathers all six.

## Why

One page rendered every printable in one long scroll. Three things were wrong
with that: it gave a graph-paper sheet and the calendar maker the same weight,
the only way to browse was to keep scrolling, and the page carried the search
weight for six quite different topics at once.

Splitting by category gives each group a real page with its own title,
description and URL — something to rank for "printable graph paper and grids"
rather than trying to rank one page for everything.

## The URLs, and why they are spelled out

The slug is a separate field on each entry in `AP.CATEGORIES`, not the `id`,
because three ids make bad public URLs:

| id | slug | why not the id |
|---|---|---|
| `labels` | `cards-and-labels` | `/labels/` is already a printable's landing page |
| `home` | `home-and-life` | `/home/` reads like the site root, not a category |
| `fun` | `games-and-puzzles` | `/fun/` says nothing to someone reading the address bar |
| `calendars` | `calendars-and-planners` | too close to the `/calendar/` landing page |

The build asserts nothing here — but `tools/build-categories.mjs` and
`tools/build-landing.mjs` both write into `docs/<slug>/`, so a slug that
collided with a printable id would have one silently overwrite the other. If
you add a category, check the slug against `docs/` first.

## What they are made of

Static HTML, no JavaScript — the same bargain the landing pages make. Their job
is to answer a browse or a search and hand the visitor to a maker, and sign-in
is not part of that (see `accounts.md`).

The cards are one design, drawn from `docs/assets/js/art.js` so a tweak cannot
land on one page and not another. The generator inlines the art at build time;
the marketing page at all-printable.com loads the same file in the browser to
draw its category cards. Before this the art lived inside `home.js`, where the
generator could not reach it.

Each page carries `CollectionPage` structured data with an `ItemList` of its
printables, and links to the other five categories at the foot.

## What changed around them

- The header nav links to the six category pages instead of home-page anchors.
- Landing-page breadcrumbs point at the category page, not `index.html#<cat>`.
- The sitemap gained the six URLs, at priority 0.8 — above the makers, below
  the landing pages that target a named search.
- The home hero's third button was "See everything", pointing at `#calendars`.
  That anchor no longer exists; it is now "Browse by category". That page has
  since moved to the all-printable-www repo.

## Rebuilding

    node tools/build-categories.mjs   # the six category pages
    node tools/build-landing.mjs      # landing pages, and the sitemap

Run the landing build second: it writes `sitemap.xml`, which includes the
category URLs.

## The index at `/`

This host used to serve a copy of the marketing home page — the same hero,
comparison table and FAQ that all-printable.com serves. Two live domains
carrying the same page is duplicate content, and it was not what the 33 pages
linking here as "All printables" were asking for.

`/` is now the catalogue: every printable, grouped under its six category
headings, each heading linking to the category page. It is also the only page
that lists all 26 at once — something nothing had after the home page stopped
showing them.

It is generated, not hand-written, so it cannot fall behind the registry. It
loads the same three scripts the old index did (`util`, `analytics`,
`account`), minus the two that rendered cards in the browser, which the
generator now does at build time.
